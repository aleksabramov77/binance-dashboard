# 0055 · Переключение прода на свою VM apps-tokyo, уход с Vercel

- **Тип:** feature
- **Статус:** approved
- **Раздел PRD:** §3.4 Авто-бот (хостинг)
- **Дата:** 2026-10-17

## Цель
Шаг 2 ухода с Vercel (после 0017 и 0048). Прод — сайт, API, тик движка, фоновые задачи и бот Telegram — переходит
на VM `apps-tokyo` (`https://binance.<ip>.sslip.io`). Vercel перестаёт получать выкатки и неделю остаётся
резервом. База остаётся в Supabase Postgres; переход на SQLite — следующая задача.

## Сценарии
1. После мержа каждый зелёный CI на `main` сам выкатывает VM, как раньше Vercel. Vercel новых сборок не делает.
2. Тик движка, снимок Earn, монитор и место в БД, демо- и авто-зеркало выполняет VM: `engine_state.runner = oracle`.
   Задания pg_cron в Supabase сняты.
3. Бот Telegram (`/db`, `/help`) отвечает с VM.
4. Демо-зеркало торгует с VM. Demo-ключи кладутся на VM, решение владельца 2026-10-17.
5. Если что-то пошло не так, откат одной последовательностью из runbook: `runner → supabase`, вернуть задания pg_cron,
   webhook на Vercel.

## Вне scope
- SQLite и отключение Supabase — задача 4 очереди.
- Ключ реального аккаунта: «Портфель» и сложные продукты Earn на VM показывают «ключ не настроен» до задачи 5.
- Выкатка `binance-live` — задача 3 очереди. `LIVE_APP_URL` воркера после переключения — адрес VM; его ставит
  владелец вместе с секретами воркера.
- Удаление проекта Vercel — через неделю, с согласия владельца.

## Технические заметки
- Роуты `/api/cron/*` на Vercel `runner` не проверяют. Поэтому `runner → oracle` и снятие заданий pg_cron делаются
  одной серией, чтобы задачи не выполнились дважды. Окно между ними — секунды.
- Edge Function `engine-tick` при `runner = oracle` — no-op; её задание тоже снимается.
- Vercel после `deploymentEnabled.main = false` держит последнюю выкатку: это резерв с той же базой. Тик там не идёт.
