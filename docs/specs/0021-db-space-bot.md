# 0021 · Telegram-бот: свободное место в базе

- **Тип:** feature
- **Статус:** approved
- **Раздел PRD:** §3.6 [Логи и обработка ошибок](../PRD.md#36-логи-и-обработка-ошибок--запрос-пользователя-2026-10-09)
- **Дата:** 2026-10-15

## Цель
База на Supabase Free ограничена 500 МБ, и сейчас не видно, сколько места осталось. Владелец хочет спрашивать
бота `@binance_dashboard_gold_bot` о свободном месте и получать сообщение, когда свободного места остаётся
50, 40, 30, 20, 10 и 5 % — чтобы успеть почистить данные или переехать до того, как база упрётся в лимит.

## Сценарии
1. Владелец пишет боту `/db` и получает размер базы, лимит, свободное место в МБ и % и три самые большие
   таблицы.
2. База растёт. Монитор раз в 15 минут видит, что свободного места ≤ 30 %, и один раз присылает
   «⚠️ Свободного места в базе ≤ 30 %» с цифрами. На следующих прогонах повтора нет, пока не пройден следующий
   порог (20 %).
3. Владелец почистил данные, свободного места снова > 32 %. Порог 30 % «перезаряжается»: если база снова
   дорастёт до него, придёт новое сообщение.
4. Посторонний пишет боту `/db` и не получает ответа.

## Критерии приёмки
- [ ] AC1. `POST /api/telegram/webhook` с заголовком `X-Telegram-Bot-Api-Secret-Token`, равным
  `TELEGRAM_WEBHOOK_SECRET`, и сообщением `/db` (или `/db@<бот>`) из чата `TELEGRAM_CHAT_ID` → ответ боту
  в этот чат: «💾 База: занято X МБ из L МБ, свободно Y МБ (P %)» и до трёх самых больших таблиц с размерами.
  Ответ маршрута — 200.
- [ ] AC2. `/start` и `/help` от владельца → список команд бота. Неизвестная команда или текст → тот же список.
- [ ] AC3. Неверный или отсутствующий секрет → 401, бот ничего не отправляет. Если `TELEGRAM_WEBHOOK_SECRET`
  не задан → 503. Сообщение из чужого чата → 200, бот ничего не отправляет, в журнале — warn
  `telegram.foreign` с chat id.
- [ ] AC4. Маршрут `/api/telegram/webhook` доступен без входа через GitHub (как `/api/cron/*`), остальные
  `/api/*` по-прежнему требуют входа.
- [ ] AC5. `POST /api/cron/log-monitor` дополнительно проверяет место. В JSON-ответе есть
  `dbSpace: { usedBytes, limitBytes, freePct, notified }`, где `notified` — порог, о котором отправлено
  сообщение в этом прогоне, или `null`.
- [ ] AC6. Пороги свободного места — 50, 40, 30, 20, 10, 5 %. При первом прохождении порога приходит одно
  сообщение «⚠️ Свободного места в базе ≤ N %» с цифрами и ссылкой на `/logs`. Повторный прогон без изменений
  ничего не шлёт. Если за прогон пройдено сразу несколько порогов (например, 55 % → 25 %), приходит одно
  сообщение о самом низком (30 %), а остальные помечаются отправленными.
- [ ] AC7. Если свободного места стало больше «порог + 2 п.п.», порог перезаряжается и при следующем прохождении
  снова присылает сообщение. Состояние хранится в `alert_state` (ключи `db.space.<N>`), новой миграции нет.
- [ ] AC8. Лимит задаётся `DB_SIZE_LIMIT_MB` (по умолчанию 500). Некорректное значение → 500 и warn в журнале.
- [ ] AC9. Ошибка замера места не ломает монитор журнала: ответ cron — 200 с результатом монитора и
  `dbSpace: { error }`, ошибка — в журнале. Без настроенного Telegram замер и состояние порогов работают,
  отправка пропускается (как у монитора).
- [ ] AC10. `pnpm telegram:setup` регистрирует webhook на `${SITE_URL}/api/telegram/webhook` с секретом и меню
  команд бота. `pnpm telegram:setup --delete` снимает webhook.

## Вне scope
- Автоочистка базы при нехватке места (только уведомления).
- Показ места в интерфейсе дашборда.
- Другие команды бота, кроме `/db`, `/start`, `/help`.
- Замер места для SQLite на Lightsail: это этап 3 миграции. Сейчас замер сделан одной функцией `getDbUsage()`,
  чтобы на этапе 3 заменить только её.

## Технические заметки
- Затронутые FSD-слайсы:
  - новый `features/db-space`: `config` (пороги), `lib/planSpaceAlerts` и `lib/formatDbSpace` — чистые
    функции с тестами;
  - `shared/api/telegram`: `setWebhook`, `deleteWebhook`, `setMyCommands`;
  - `shared/config/env.server`: `DB_SIZE_LIMIT_MB`, `TELEGRAM_WEBHOOK_SECRET`;
  - `shared/lib/auth/accessPolicy`: публичный префикс `/api/telegram/`.
- Композиция (платформа):
  - `src/app/server/dbSpace.ts`: `getDbUsage()` через `pg_database_size(current_database())` и
    `pg_total_relation_size` по `pg_stat_user_tables`; `checkDbSpace()`.
  - `src/app/server/telegramBot.ts`: `handleTelegramUpdate`.
  - Загрузку и сохранение `alert_state` переиспользовать из `logMonitor.ts`: вынести в общий модуль.
- Маршруты: `app/api/telegram/webhook/route.ts` (новый); `app/api/cron/log-monitor/route.ts` дополнительно
  вызывает `checkDbSpace()` в своём try/catch.
- Скрипт `scripts/telegram-setup.ts` → `pnpm telegram:setup [--delete]`. При включённом webhook `getUpdates`
  (`fetchTelegramChats`) не работает: chat id владельца уже известен, `--delete` вернёт прежнее поведение.
- Env: `TELEGRAM_WEBHOOK_SECRET`, `DB_SIZE_LIMIT_MB` — в `.env.example` и `.env.local` синхронно, в PRD §4.
  После выкатки: секрет — в Vercel, затем один раз `pnpm telegram:setup`.
- Риски: размер на PGlite локально считается тем же запросом — цифры другие, но логика та же. Supabase
  считает лимит по размеру базы на диске; `pg_database_size` даёт ту же величину.
