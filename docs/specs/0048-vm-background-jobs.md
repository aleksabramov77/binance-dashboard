# 0048 · Фоновые задачи на своей VM: таймеры вместо pg_cron

- **Тип:** feature
- **Статус:** approved
- **Раздел PRD:** §3.4 Авто-бот (хостинг)
- **Дата:** 2026-10-16

## Цель
Первая задача ухода с Vercel (после 0017). Сейчас pg_cron в Supabase вызывает роуты на Vercel. На своей VM
процесс живёт постоянно, поэтому те же задачи запускает он сам по таймерам — так уже работает тик движка.
Чтобы задачи не выполнялись дважды (Vercel по крону и VM по таймеру), таймер VM срабатывает, только когда
`engine_state.runner` = роль процесса (`ENGINE_RUNNER=oracle`). Сейчас там `supabase`, поэтому после мержа
ничего не меняется. Задачи VM включатся вместе с тиком на переключении (следующая задача).

## Сценарии
1. `runner = supabase` (сейчас): таймеры на VM срабатывают и сразу пропускают работу, без записей в БД и
   журнал. Прод работает как раньше через pg_cron и Vercel.
2. `runner = oracle` (после переключения): VM сама делает:
   - снимок Earn в 03:00 и 15:00 UTC;
   - монитор журнала и проверку свободного места в базе раз в 15 минут;
   - демо-зеркало раз в минуту, после тика;
   - авто-зеркало в 07:00 UTC.
   Расписание то же, что у pg_cron.
3. Предыдущий запуск задачи ещё идёт → следующий пропускается, задачи не накладываются.

## Критерии приёмки
- [ ] AC1. Модуль фоновых задач (`src/app/server/backgroundJobs.ts` или рядом с `experimentEngine.ts`):
  - запускается из `instrumentation.ts` вместе с таймером движка, только вне Vercel;
  - выполняет те же функции, что роуты `/api/cron/*`: `collectSnapshot`, `runLogMonitor` + `checkDbSpace`,
    `runDemoMirror`, `runMirrorAuto`. Логика не дублируется.
- [ ] AC2. Расписание в UTC совпадает с pg_cron: `0 3,15 * * *`, `*/15 * * * *`, `* * * * *`, `0 7 * * *`.
  Время следующего запуска считает чистая функция с тестами.
- [ ] AC3. Перед каждым запуском проверяется, что процесс не на Vercel, роль процесса (`getRunnerRole`) совпадает
  с `readRunner` из БД, а прошлый запуск этой задачи закончился. Иначе запуск пропускается: одна запись debug, без
  записей в журнал БД. Тесты на все три условия.
- [ ] AC4. Сбой задачи не роняет процесс и другие задачи: ошибка пишется в журнал с тем же событием, что у
  роута (`cron.earn`, `cron.monitor`, `cron.mirror`, `cron.mirror_auto`). Следующий запуск — по расписанию.
- [ ] AC5. Роуты `/api/cron/*` остаются: они нужны для pg_cron, пока прод на Vercel, и для ручного запуска.
- [ ] AC6. На VM после выкатки ветки при `runner = supabase` в журнале БД нет записей этих задач с `source = vm`, а
  в журнале сервиса видны пропуски (debug). Прод на Vercel и pg_cron работают как раньше.
- [ ] AC7. `pnpm check` и `pnpm build` зелёные. `docs/ai/deploy-lightsail.md` и `docs/ai/architecture.md` описывают,
  кто и когда запускает задачи.

## Вне scope
- Само переключение (`runner → oracle`, выключение заданий pg_cron, webhook Telegram, автодеплой) — задача 0049.
- SQLite, ключ реального аккаунта, бэкапы — следующие задачи плана.

## Технические заметки
- Затронутые слайсы: `src/app/server/*` (композиция), `instrumentation.ts`. Фичи `collect-snapshot`, `demo-mirror` и
  монитор не меняются.
- Зеркало уже защищено блокировкой параллельных прогонов (0012, часть 2e). Таймер её не обходит, а лишь не
  запускает второй прогон из того же процесса.
- Демо-зеркало на VM без demo-ключей (решение владельца 2026-10-15) отвечает «не настроено». Включать ли ключи на
  VM — вопрос к владельцу на переключении (0049).
