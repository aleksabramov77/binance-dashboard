# 0037 · Алерт монитора → задача в GitHub → Claude разбирает и готовит draft PR

- **Тип:** feature
- **Статус:** approved
- **Раздел PRD:** §3.6 Логи и обработка ошибок
- **Дата:** 2026-10-16

## Цель
Сейчас тревога монитора приходит в Telegram, а разбор и фикс запускает пользователь вручную (`/flow bug …`). Нужно,
чтобы новая тревога сама заводила задачу и запускала Claude. Claude собирает факты, решает, баг ли это в коде, и если
да — готовит фикс до draft PR. Мерж и выкатка остаются за пользователем (решение пользователя 2026-10-16).

## Сценарии
1. Монитор находит **новую** проблему → создаёт issue в приватном репозитории `aleksabramov77/binance-dashboard-private`
   с меткой `alert`: заголовок тревоги, детали, ИИ-разбор, до 15 свежих записей журнала, ссылка на `/logs`.
   Сообщение в Telegram — как раньше, плюс строка «🤖 Claude разбирает: <ссылка на issue>».
2. Метка `alert` запускает routine Claude Code в облаке (webhook-триггер GitHub). Routine работает по
   `.claude/routines/alert-triage.md`:
   - не баг в коде (сбой Binance или Supabase, рассинхрон версий, разовый всплеск) → комментарий с разбором в issue,
     метка `alert-no-code`, кода нет;
   - баг в коде → ветка `bug/NNNN-slug`, spec, сначала падающий тест, потом фикс, `pnpm check && pnpm build`,
     **draft PR** в публичный `binance-dashboard`, комментарий в issue со ссылками на PR и сессию, метка `alert-pr`.
   В конце — сообщение в Telegram «✅ draft PR готов: …» или «ℹ️ разбор без кода: …».
3. Повтор той же незакрытой тревоги (напоминание раз в 2 ч) → новый issue не создаётся. В открытый issue с тем же
   ключом добавляется комментарий «повтор: <детали тревоги>» (для счётчиков — «повтор: N … за 15 мин», например
   «повтор: 5 ответов 5xx за 15 мин»), второй строкой — время; routine повторно не запускается.
4. За сутки уже создано `ALERT_AUTOFIX_PER_DAY` (по умолчанию 3) issue с `alert` → новый issue создаётся с меткой
   `alert-queued` (Claude не запускается). В Telegram: «📝 Задача: <ссылка> (лимит автозапусков на сутки)».
   Запустить вручную — сменить метку на `alert`.
5. GitHub недоступен или `GITHUB_ALERTS_TOKEN` не задан → уведомление в Telegram уходит как раньше, без строки про
   задачу; сбой GitHub — `warn monitor.github` в журнале.

## Критерии приёмки
- [ ] AC1. Новая проблема → ровно один issue в репозитории из `GITHUB_ALERTS_REPO` с меткой `alert`. В теле —
  невидимый маркер `<!-- alert:<key> -->`, заголовок, детали, ИИ-разбор (если есть), записи журнала и ссылка `/logs`.
- [ ] AC2. Повторное уведомление о той же активной проблеме → комментарий в открытый issue с этим маркером, нового
  issue нет.
- [ ] AC3. Сверх `ALERT_AUTOFIX_PER_DAY` за 24 ч issue получает метку `alert-queued` вместо `alert`; в Telegram это
  указано.
- [ ] AC4. В тексте Telegram есть ссылка на issue. Если GitHub упал или токена нет, уведомление уходит без неё, а
  состояние алертов сохраняется как раньше; сбой GitHub записан в журнал как `warn monitor.github`.
- [ ] AC5. Без `GITHUB_ALERTS_TOKEN` (локально, на сервере worktree) поведение монитора прежнее — существующие тесты
  `runMonitor` зелёные.
- [ ] AC6. `.claude/routines/alert-triage.md` описывает routine: что читать, как решить «баг или нет», шаги до draft PR,
  запреты (без мержа, без записи в прод-БД, без данных журнала и названий приватных экспериментов в публичном PR),
  метки и сообщение в Telegram.
- [ ] AC7. Метки `alert`, `alert-queued`, `alert-no-code`, `alert-pr` существуют в репозитории; если метки нет, код
  создаёт её при первом issue.
- [ ] AC8. Тесты на создание, дедуп и лимит (мок `fetch`) падали бы без фичи; `pnpm check` и `pnpm build` зелёные.
- [ ] AC9 (на этапе выкатки, с пользователем). Routine создана, webhook-триггер `issues.labeled = alert` на
  приватном репо подключён. Тестовый issue с `alert` запускает сессию (`RemoteTrigger list_runs`), и она оставляет
  комментарий в issue.

## Вне scope
- Разбор текста сообщений Telegram и кнопки в боте: триггер ставится у источника, в мониторе.
- Автомерж и автовыкатка, запись в прод-БД из routine.
- Доступ routine к прод-журналу: факты берутся из тела issue.
- Тревоги «места в базе» (`db.space.*`): у них свой поток, они не про код.

## Технические заметки
- `src/shared/api/github/` — серверный клиент REST (только `fetch`, Zod-схемы ответов): найти открытый issue по
  маркеру (`GET /search/issues` или список с меткой), создать issue, комментарий, создать метку при её отсутствии,
  посчитать issue с меткой `alert` за 24 ч. Без доменных слов — `shared` не знает о мониторе.
- `features/log-monitor`: чистая `formatAlertIssue(issue, analysis, samples, logsUrl)` и решение «создать /
  прокомментировать / в очередь». `runMonitor` получает необязательную зависимость `trackIssues`. Её вызывают после
  разбора ИИ и до отправки Telegram, а результат (ссылки) идёт в `formatAlert`. Ошибка `trackIssues` не мешает
  уведомлению.
- Композиция `src/app/server/logMonitor.ts`: `getGithubAlertsConfig()` в `shared/config/env.server.ts` (`GITHUB_ALERTS_TOKEN`,
  `GITHUB_ALERTS_REPO` — по умолчанию `aleksabramov77/binance-dashboard-private`, `ALERT_AUTOFIX_PER_DAY` — 3);
  новые переменные — в `.env.example` и `.env.local` (одинаковые по структуре) и в Vercel (загружает пользователь).
- Токен — fine-grained PAT только на `binance-dashboard-private`, права Issues: Read and write. Публичного репо он не
  касается.
- Почему приватный репо: в тексте тревог бывают названия и детали приватных экспериментов (spec 0015).
- Routine (этап выкатки): создаётся через `RemoteTrigger create`, промпт ссылается на
  `.claude/routines/alert-triage.md`. Репозитории — оба. Webhook-триггер — `create_webhook_trigger` (GitHub,
  `issues` / `labeled`, фильтр `alert`). Секреты Telegram для финального сообщения — в переменных облачного окружения
  routine. Если нужен GitHub App Claude на репозиториях, его ставит пользователь.
- Риски: формат тела webhook-триггера проверяет сервер при создании; если `labeled`-фильтр недоступен — триггер на
  `opened` с меткой в фильтре.
