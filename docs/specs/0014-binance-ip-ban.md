# 0014 · Binance банит IP Vercel за запрос цен для шапки лаборатории

- **Тип:** bug
- **Статус:** testing
- **Серьёзность:** major
- **Дата:** 2026-10-15

## Шаги воспроизведения
1. Прод (Vercel, регион hnd1), открыта любая страница лаборатории: шапка с бюджетами опрашивает
   `/api/experiments/budgets` раз в 30 с с каждой вкладки.
2. Для нереализованного PnL сервер берёт цены из `GET api.binance.com/api/v3/ticker/24hr` (все пары, **вес 80**) и
   `fapi.binance.com/fapi/v1/ticker/24hr` (**вес 40**). Кэш на 20 с живёт только внутри одного тёплого экземпляра
   функции.
3. Исходящий IP Vercel общий с другими клиентами: лимит Binance 6000 веса/мин на IP съедают и они.

## Ожидаемое поведение
Шапка получает цены дешёвым запросом. После ответа Binance 429/418 сервер не обращается к этому хосту Binance, пока
не кончится пауза или бан. Повторные запросы во время бана Binance наказывает удлинением бана, от минут до 3 суток.

## Фактическое поведение
Прод-журнал `app_logs`, 2026-10-14 (UTC):
- 02:45:35 `http.upstream` **429** `/api/v3/ticker/24hr`: «Too much request weight used; current limit is 6000 request
  weight per 1 MINUTE. Please use WebSocket Streams for live updates to avoid polling the API.» (-1003)
- 03:20:34 и 18:31:01 `http.upstream` **418**: «Way too much request weight used; IP banned until …» (-1003), бан до
  18:35:22.
- После каждого: `experiments.budgets` «Цены для нереализованного PnL недоступны» — шапка без нереализованного PnL.

## Причина
Цены для шапки (`lastPrices` в `src/app/server/experimentBudgets.ts`) и для сброса лаборатории (`lastPrices` в
`src/app/server/experimentSettings.ts`) брались из `ticker/24hr` без символа: вес 80 (спот) и 40 (фьючерсы), хотя
нужна только последняя цена. Кэш на 20 с живёт в одном экземпляре функции Vercel, поэтому опрос раз в 30 с с каждой
вкладки почти всегда шёл в Binance. Лимит 6000/мин считается на исходящий IP Vercel, общий с чужими приложениями.
`getJsonWithRetry` (`src/shared/lib/fetchRetry.ts`) не помнил о 429/418, и следующий опрос во время бана снова шёл в
Binance, хотя повтор во время бана его удлиняет.

**Фикс:** `fetchTickerPrices(market)` (`ticker/price`, вес 4/2) для обоих потребителей; в `getJsonWithRetry` — пауза
на хост после 429/418 (`Retry-After` → «banned until» → 60 с) с записью `binance.cooldown`.

## Критерии приёмки
- [ ] AC1. Цены для шапки (`experimentBudgets.ts`) и для сброса лаборатории (`experimentSettings.ts`) берутся из
  `ticker/price` (спот `/api/v3/ticker/price` — вес 4, фьючерсы `/fapi/v1/ticker/price` — вес 2) вместо `ticker/24hr`.
  Где возможно, используется существующий `fetchTickerPrices` (`src/shared/api/binance/client.ts`). Шапка на локальном
  сервере показывает нереализованный PnL как раньше.
- [ ] AC2. После ответа Binance **429 или 418** серверные запросы через `getJsonWithRetry` к тому же хосту не уходят в
  сеть до конца паузы: срок из заголовка `Retry-After`; для 418 — из «banned until <ms>» в теле, если он позже; без
  обоих — 60 с. Вызов во время паузы сразу бросает понятную ошибку («Binance: пауза до HH:MM:SS после 429/418»).
- [ ] AC3. Пауза ставится один раз и пишет одну запись в журнал (`binance.cooldown`, warn, хост и срок), без записи
  на каждый пропущенный вызов.
- [ ] AC4. Есть тесты, которые падали до фикса: (а) после 418 следующий вызов к тому же хосту не делает `fetch`, а
  после срока — делает; (б) пауза одного хоста не блокирует другой (`api.binance.com` ≠ `fapi.binance.com` ≠ demo).
- [ ] AC5. `pnpm check && pnpm build` зелёные.

## Вне scope
- Тик движка в Edge Function Supabase (свой `getJson`, другой IP, ошибок лимита не было).
- WebSocket-потоки цен и переезд на свою VM — план миграции, отдельные задачи (Lightsail, этапы 1–7).
- Общий для всех экземпляров Vercel учёт паузы (в БД): пауза живёт в памяти экземпляра. Этого достаточно, потому что
  после фикса шапка тратит ~4–8 веса за запрос вместо 120.
