# 0047 · Реальный счёт: торговый ключ субсчёта, проверка прав и воркер без торговли

- **Тип:** feature (задача 2 эпика «Реальные деньги», PRD §3.7)
- **Статус:** approved
- **Раздел PRD:** §3.7 [Реальный счёт (Live)](../PRD.md#37-реальный-счёт-live-)
- **Дата:** 2026-10-16

## Цель
Первый шаг к торговле реальными деньгами (решение пользователя 2026-10-16). Отдельный субсчёт Binance с ключом,
у которого есть только торговля и чтение. Выводов и переводов у ключа нет: деньги между счетами пользователь
переводит руками. Задача подключает этот ключ безопасно и показывает, что он годится, **но сделок не открывает**.
Сделки — следующая задача эпика («Реальное зеркало»).

## Решения пользователя (2026-10-16)
1. Сделки — на **субсчёте** Binance с изолированным ключом: только чтение и торговля. Выводы, внутренние и
   универсальные переводы ключу не разрешаются. Все перемещения денег пользователь делает руками.
2. Ключ живёт на **Lightsail VM** с постоянным IP (whitelist ключа) — не на Vercel и не в Supabase. VM делает сессия
   «Migration to AWS» (этапы 1–2 плана переезда, задача 0017).
3. Рынки — **спот и USDⓈ-M фьючерсы**.
4. Лимиты на старте (для задачи 3): $10 на сделку, до 5 открытых позиций, −$15 за сутки → стоп новых входов.
5. Допуск эксперимента (задача 3): режимы как у демо-зеркала 0043 («Выкл · Авто · Вкл») и ещё «Вкл + автовыключение
   по заданным параметрам».
6. Эпик по задачам: VM → **0047 (эта)** → реальное зеркало → статистика Real.

## Сценарии
1. Пользователь по инструкции на `/settings` создаёт субсчёт и ключ с IP VM, кладёт ключ в env воркера на VM и
   запускает воркер. Через минуту карточка «Реальный счёт» показывает «✅ Ключ годится · торговля выключена»:
   права ключа, IP-ограничение, остатки Spot и USDⓈ-M субсчёта.
2. Пользователь по ошибке включил ключу «Enable Withdrawals». Воркер при проверке видит это и ставит блокировку.
   Карточка — «⛔ Ключ заблокирован: у ключа разрешён вывод средств — выключите в настройках ключа». В Telegram
   приходит одно сообщение. Пока причина не исправлена, воркер ничего, кроме проверки прав, на бирже не делает.
3. Ключ по ошибке создан на основном счёте, а не на субсчёте → «⛔ Это ключ основного счёта — нужен ключ субсчёта».
4. Воркер упал или VM выключена → через 5 минут карточка: «⚠️ Воркер молчит с 12:03». Монитор присылает тревогу.
5. Воркер ещё ни разу не запускался → «Не подключён» и инструкция «Как подключить».

## Критерии приёмки
- [ ] AC1. **Клиент реального счёта — только чтение и торговля.** Подписанные запросы с ключом `BINANCE_TRADE_*`
  уходят только через отдельный клиент, у которого есть белый список «метод + хост + путь». Запрос вне списка
  бросает ошибку до сети. В этой задаче в списке только чтение: права ключа, аккаунт Spot, баланс/аккаунт USDⓈ-M.
  Юнит-тест проверяет, что пути вывода, переводов и займов (`withdraw`, `transfer`, `capital`, `sub-account`,
  `loan`/`borrow`, `universal`) отвергаются и ни один из них не попадает в белый список, даже если его туда добавят.
- [ ] AC2. **Проверка прав ключа** (`GET /sapi/v1/account/apiRestrictions`) — при старте воркера и каждые 10 минут.
  Ключ **годится**, если: `ipRestrict = true`, `enableReading = true`, `enableSpotAndMarginTrading = true`,
  `enableWithdrawals = false`, `enableInternalTransfer = false`, `permitsUniversalTransfer = false`,
  `enableMargin = false`. `enableFutures = false` — не блокировка, а предупреждение «фьючерсы недоступны». Любое
  нарушение или неизвестный ответ → блокировка с понятной причиной по-русски (по каждому нарушенному пункту).
  Чистая функция оценки покрыта тестами на каждое правило.
- [ ] AC3. **Не основной счёт.** UID субсчёта из аккаунта Spot сравнивается с UID основного счёта по read-only ключу.
  Совпали → блокировка «Это ключ основного счёта». Read-only ключа нет → проверка пропускается с пометкой в карточке.
- [ ] AC4. **Воркер реального счёта** — отдельный Node-процесс (`pnpm live:worker`; на VM — свой systemd-сервис под
  своим пользователем). Ключ Binance есть только у него; у веб-приложения ключа нет. Раз в минуту воркер шлёт «пульс»
  в приложение: `POST /api/live/heartbeat`, Bearer `LIVE_WORKER_SECRET`. В пульсе — оценка прав, причины блокировки,
  UID-проверка, остатки субсчёта (Spot — USDT free + locked и equity в $; USDⓈ-M — walletBalance, availableBalance,
  unrealizedProfit) и версия воркера. Без верного секрета — 401. Данные — в БД (последний пульс), ключ и секрет
  в пульс и журнал не попадают. `pnpm live:build` собирает воркер в один файл `dist/live-worker.mjs`. Он запускается
  `node dist/live-worker.mjs` без `node_modules` и делает то же, что `pnpm live:worker`.
- [ ] AC5. **Карточка «Реальный счёт»** на `/settings`: состояния «Не подключён», «✅ Ключ годится · торговля
  выключена», «⛔ Ключ заблокирован: <причины>», «⚠️ Воркер молчит с <время>» (пульса нет > 5 мин). Кроме того:
  - список прав ключа галочками;
  - остатки Spot и USDⓈ-M;
  - время последнего пульса;
  - блок «Как подключить» — шаги на Binance (ниже) с точными английскими названиями кнопок.
- [ ] AC6. **Шапка:** R в чипах групп `SPOT` и `FT:USDM` и в поповере — остатки **торгового субсчёта** из пульса
  (подсказка «субсчёт, пульс <время>»). Нет пульса → «—» с причиной. `FT:COINM` — «—» «COIN-M на реальном счёте не
  торгуется».
- [ ] AC7. **Telegram и журнал:** смена состояния (годится ↔ заблокирован, воркер замолчал ↔ вернулся) → одна запись
  `live.status` в `/logs` и одно сообщение в Telegram, без повторов, пока состояние держится. «Воркер молчит» ловит
  монитор (новое правило) — только если воркер хоть раз присылал пульс.
- [ ] AC8. **Пустые и ошибочные состояния.** Нет `BINANCE_TRADE_API_KEY/SECRET` у воркера → он шлёт пульс «ключ не
  задан». Биржа недоступна, 429/418 → пульс с ошибкой; блокировка не снимается, пауза — по общим правилам
  `fetchRetry`. Ошибка 401/`-2015` (неверный ключ или не тот IP) → блокировка «Binance не принял ключ: проверьте ключ
  и IP-whitelist».
- [ ] AC9. **Документация:** `.env.example` и `.env.local` — раздел «Реальный счёт (только VM)»: `BINANCE_TRADE_API_KEY`,
  `BINANCE_TRADE_API_SECRET`, `LIVE_WORKER_SECRET`, `LIVE_APP_URL`, с комментарием, где задаются (env воркера на VM;
  `LIVE_WORKER_SECRET` — ещё на Vercel). Глоссарий — «Реальный счёт», «Субсчёт», «Воркер реального счёта», «Пульс»
  (`pnpm glossary`). README `shared/api/binance` — четвёртый «мир» (Live).

## Подготовка на Binance (руками, пользователь)
Текст для блока «Как подключить» и PRD. Точные названия кнопок сверить с текущим интерфейсом Binance при реализации.
1. Основной счёт: **Account → Sub Accounts → Create Sub Account** (нужны KYC и 2FA). Почта — виртуальная.
2. Субсчёту включить фьючерсы: **Sub Accounts → Account Management → [субсчёт] → Futures → Enable**.
3. Перевести деньги на субсчёт руками: **Sub Accounts → Asset Management → Transfer** (основной Spot → субсчёт Spot,
   затем внутри субсчёта Spot → USDⓈ-M). Старт — $80–100.
4. Ключ субсчёта, когда известен постоянный IP VM: **Sub Accounts → API Management → [субсчёт] → Create API**.
   Включить только **Enable Reading**, **Enable Spot & Margin Trading**, **Enable Futures**. **Restrict access to
   trusted IPs only** → IP VM. Не включать **Enable Withdrawals**, **Enable Internal Transfer**, **Permits Universal
   Transfer**, **Enable Margin Loan, Repay & Transfer**.
5. Ключ и секрет — в env воркера на VM (файл только для пользователя воркера), не в чат и не на Vercel.

## Технические заметки
- **Почему отдельный воркер:** ключ с правом торговли не лежит в веб-процессе, который принимает запросы из
  интернета. Воркер не принимает входящих соединений и знает только ключ, секрет пульса и адрес приложения;
  `DATABASE_URL` ему не нужен. Канал «пульс» — первая часть связи воркер ↔ приложение, задача 3 добавит в него
  задания на ордера.
- **FSD:** клиент — `shared/api/binance/live.server.ts` (+ чистые `liveAllowlist.ts`, `liveRestrictions.ts` с
  тестами); состояние — `entities/live-account` (схема пульса Zod, чтение/запись последнего пульса, решение
  «молчит»); карточка — `pages/settings/ui/LiveAccountCard.tsx` или `widgets`; R в шапке —
  `src/app/server/accountBalances.ts` (Real из пульса вместо read-only ключа); маршрут — `app/api/live/heartbeat`
  (`withLogging`, своя авторизация по секрету, публичен в `accessPolicy`, как webhook Telegram); воркер —
  `scripts/live-worker.ts` (`--once` для проверки).
- **Установка на VM** (из 0017, сообщение сессии «Migration to AWS» 2026-10-16): VM `apps-tokyo` с постоянным IP
  создана. IP не пишется в публичный репозиторий. Воркер ставится командой
  `scripts/server/add-project.sh <имя> --no-web` — свой Linux-пользователь, env в `/etc/<имя>/app.env` (640), свой
  systemd-unit, без Caddy. Скрипт появится в PR 0017; в этой задаче — только команда запуска воркера и описание env.
  Раскладка, согласованная с 0017:
  - пользователь и сервис `binance-live`, env в `/etc/binance-live/app.env`;
  - **бандл делает 0047:** `pnpm live:build` → esbuild, один файл `dist/live-worker.mjs` (ESM, target node22, все
    зависимости внутри, на VM без node_modules); unit запускает его как `node live-worker.mjs`;
  - журнал воркера — stdout/stderr (journald), файлов он не пишет и в Postgres не ходит;
  - в Telegram воркер не ходит — сообщения шлёт приложение по пульсу;
  - исходящие: `api.binance.com`, `fapi.binance.com`, хост `LIVE_APP_URL` (до переезда — Vercel, после — VM; меняется
    только env).
- **Хосты Live:** `api.binance.com` (Spot, `/sapi`), `fapi.binance.com` (USDⓈ-M). Подпись — существующий
  `signedRequest`; белый список проверяется до него.
- **Изменение решения:** раньше PRD говорил «ключ реального аккаунта на сервер не кладём». Теперь кладём только
  торговый ключ субсчёта, только на VM, только в воркер (решение пользователя 2026-10-16).
- **Проверка на локальном сервере:** реального ключа локально нет. Состояния карточки тестировщик получает воркером:
  - без ключа → «ключ не задан»;
  - для остальных состояний — фикстура воркера `--fixture ok|blocked|main-account`. Она шлёт пульс с готовыми
    данными, без похода на биржу, и запрещена, если задан ключ или адрес приложения не localhost;
  - «молчит» — остановить воркер (порог для локальной проверки можно уменьшить env-переменной).
- **Риск:** `apiRestrictions` — эндпоинт `/sapi`, вес и формат сверить с документацией Binance при реализации.
  Неизвестные поля не ломают схему, а отсутствие обязательного поля — блокировка.
