# Карточка гипотезы

Каждая идея нового эксперимента — карточка по этому шаблону. Карточка с вердиктом `pursue` становится записью
в `private/experiments.json` (этап experiment `/flow lab`) и строкой бэклога `private/lab/hypotheses.md`. Всё это —
приватный репозиторий: в публичные файлы карточки не попадают.
Номер `H<n>` — сквозной по всем прогонам (последний — в `hypotheses.md`).

```markdown
### H<n>. <короткое имя>  — вердикт: pursue | revise | discard

**Механизм.** Одно предложение: кто ошибается и почему цена должна пойти в нашу сторону.

**Основание.** Откуда идея: эксперимент(ы) и цифры из отчёта (`review.md`), или эффект из литературы.
Сила: сильная (своя статистика 100+ сделок) | средняя (30–99 / литература) | слабая (наблюдение).

**Конфиг.** Рынок, id (`PSxx`/`PFxx` — следующий свободный в `private/experiments.json`), ТФ, вход, стоп, цель,
трейлинг/безубыток/тайм-стоп, юниверс, направления, фильтр тренда, maxOpen. Чем отличается от базового
эксперимента — **одно** изменение (или «смена архетипа»). Нужен ли новый код в trading-core — «сейчас» (хватает существующих блоков) или «ждёт блок: <какой>» (тип
входа/выхода/фильтра заводится отдельной задачей `/flow feature`, без параметров удачной комбинации).

**JSON для `private/experiments.json`.** Готовый элемент массива (`experimentSchema` из `trading-core`; поля
`initialBudget`, `enabled`, `demoMirror` — по умолчанию 10 000 / `true` / `false`, пишутся только при вставке):
```json
{
  "id": "PF01",
  "market": "futures",
  "name": "Пример: шорт пробоя Donchian-30 на 4h",
  "hypothesis": "Вымышленный пример формата: пробой минимума 30 свечей 4h продолжается вниз; выход по времени через 20 баров.",
  "config": {
    "timeframe": "4h",
    "entry": { "type": "donchian", "period": 30 },
    "exit": { "stop": { "type": "atr", "mult": 2 }, "takeProfit": null, "timeStopBars": 20 },
    "universe": { "type": "top", "n": 15 },
    "directions": ["short"],
    "maxOpen": 3
  }
}
```
Константы `catalog.ts` (`TOP30`, `BOTH`, `ATR15_RR2`…) в JSON недоступны — конфиг пишется явно (подсмотреть их
значения в `catalog.ts`). Проверка — `pnpm lab:private --dry-run` (схема, лишние поля, префикс ↔ рынок, повторы).
Новый тип входа/выхода/фильтра — сначала блок в `trading-core` (`strategies.ts`/`exits.ts` + тесты,
`describeConfig.ts`) отдельной задачей `/flow feature`; до её выкатки карточка — «ждёт блок».

**Сравниваем с.** Базовый эксперимент (семейство) и контроль рынка (S19 / F19; BTC за период вместо hold).

**Сколько ждать.** Ожидаемый темп сделок в день (по базовому эксперименту) → дата, когда будет 30 и 100 закрытых.

**Kill (остановить и выключить), если** — заранее, числами, например:
- после 30 закрытых avg R ≤ −0,3 или t ≤ −2;
- после 100 закрытых avg R ≤ контроля рынка;
- за 30 дней < 30 сделок (сигнал слишком редкий).

**Success (кандидат в demo-зеркало), если** — 100+ закрытых, avg R ≥ 0,2, t ≥ 2, лучше контроля, без
`concentration` (`failure-modes.md`), не хуже соседей по семейству.

**Риски.** Чем гипотеза может оказаться ложной ещё до данных (режим, комиссии, редкость, подгонка).
```

## Вердикты

- `pursue` — механизм есть, конфиг выражается (или нужен понятный новый тип входа), не дублирует
  существующий эксперимент и бэклог, kill-критерии числовые.
- `revise` — идея здравая, но конфиг или критерии надо уточнить, или она меняет больше одной вещи.
- `discard` — нет механизма, дубль, подгонка под один разрез, ожидаемый перевес меньше комиссий, или уже
  отклонялась без нового основания.

Ранжируй `pursue` по: сила основания → ожидаемая информативность (насколько результат изменит наши
решения) → дешевизна (без нового кода лучше) → темп набора сделок. Не больше 3 новых экспериментов за один
прогон, если пользователь не задал другой лимит: каждый новый — ещё одна попытка в множественных сравнениях.
