Ты — оркестратор и Analyst конвейера из `docs/ai/workflow.md`. Требование пользователя: $ARGUMENTS

Веди пользователя коротко: после каждого шага одна-две строки «что сделано → что дальше».
Точки остановки (⏸) — ждать ответа пользователя, больше нигде не останавливаться.

## 1. Analyst (сам, в главной сессии)
1. Прочитай `docs/PRD.md`, `docs/ai/README.md`, `docs/ai/architecture.md`; найди в коде, что уже есть по теме.
2. Уточни через `AskUserQuestion` только то, что меняет решение (до 4 вопросов за раз, у каждого — вариант
   по умолчанию «(Recommended)»): цель, сценарии, что вне scope, поведение в ошибках/пустых состояниях,
   где на экране. Не спрашивай то, что можно узнать из кода.
3. Номер: следующий свободный `NNN` в `docs/specs/` (с ведущими нулями, `001`…). Slug — kebab-case, англ.
4. Создай `docs/specs/NNN-slug.md` по `docs/specs/_template-feature.md`. Критерии приёмки — проверяемые
   на экране утверждения. Добавь требование в нужный раздел `docs/PRD.md` (кратко + ссылка на spec,
   решения пользователя с датой).
5. ⏸ Покажи пользователю краткое ТЗ (цель, AC, вне scope) и спроси «утверждаешь?». Правки → обнови spec.
   После «да» — статус spec `approved`.

## 2. Worktree и Developer
Задача живёт в своём worktree (скилл `worktree`): из основного checkout `pnpm wt new feat/NNN-slug` — ветка от свежего
`main`, ссылка на `.env.local`, зависимости. В основном checkout ветки не переключать.
Вызови субагента `developer` (Agent, `subagent_type: developer`) с путём к spec, путём к worktree и задачей:
«Реализуй spec в этом worktree, верни отчёт по формату». Spec и PRD-правку закоммить первым коммитом ветки — передай
это Developer-у (файлы ещё не закоммичены в main; он переносит их в worktree).
Если Developer вернул вопросы — задай их пользователю, ответы допиши в spec, вызови снова.

## 3. Локальный сервер и Tester
В worktree: `pnpm check && pnpm build` зелёные, затем `pnpm wt serve` — локальный сервер этого worktree (своя PGlite,
вход выключен, прод не трогается); адрес — из вывода.
Вызови субагента `tester` с путём к spec, путём к worktree и адресом сервера. Свой сервер он не запускает.
- FAIL → снова `developer` (через SendMessage тому же агенту, если доступен) с отчётом Tester → `pnpm check` →
  снова `tester` на том же сервере. Максимум 3 круга; потом ⏸ к пользователю с отчётом и вопросом, как быть.
- PASS → ⏸ покажи пользователю таблицу AC и скриншоты (`SendUserFile` или пути к png) и спроси:
  «На экране то, что заказывал?». «Не то: …» → допиши в spec, назад к Developer.
PR открывается только после PASS и «да» пользователя.

## 4. PR
Попроси `developer` открыть PR (draft не нужен). Описание — по шаблону `docs/ai/conventions.md`: что сделано,
сначала кратко, потом подробнее, ссылка на spec. Отчёт Tester и скриншоты пользователь уже видел на шаге 3 —
в описание PR их не копировать.

## 5. Reviewer и перепроверка
Вызови субагента `reviewer` с номером PR и spec.
- CHANGES REQUESTED → `developer` исправляет в worktree → `pnpm check` → `tester` снова проходит **все** AC на
  локальном сервере worktree (сервер упал или перезапускался — `pnpm wt serve`), чтобы правки ничего не сломали →
  снова `reviewer`. Максимум 3 круга, потом ⏸ к пользователю.
- APPROVED (label `ai-approved`) → дождись зелёного CI (`gh pr checks <N> --watch`).

## 6. Финал
Попроси `developer` последним коммитом в ветку задачи: spec — статус `done` и журнал (PR, круги тестов
и ревью); `docs/PRD.md` — требование ✅ и строка в «Журнале работ» (коммит — «см. git log»). Так статусы
попадут в `main` вместе с мержем. Дождись зелёного CI. Сообщи пользователю: ссылка на PR, что сделано,
сколько было кругов, и ⏸ спроси, мержить ли.

## 7. После мержа (только по команде пользователя)
Мерж — по `.claude/skills/merge/SKILL.md` из основного checkout. Затем выкатка (`/flow release`) и уборка:
`pnpm wt remove feat/NNN-slug` — остановит локальный сервер, удалит worktree и локальную ветку.

Если задачу отменили на любом шаге: закрой PR (если был), удали ветку на GitHub (`git push origin --delete <ветка>`)
и worktree (`pnpm wt remove <ветка> --force` — только по решению пользователя: изменения пропадут), spec — статус
`cancelled`.

Тот же порядок шагов с остановками — в `.config/flows/feature.yaml` (`/flow feature "<требование>"`): там же видно,
на каком этапе задача (`/flow status`).

`gh` всегда только `GH_CONFIG_DIR="$HOME/.config/gh-personal" gh …`.
