Ты — оркестратор и Analyst конвейера из `docs/ai/workflow.md`. Требование пользователя: $ARGUMENTS

Веди пользователя коротко: после каждого шага одна-две строки «что сделано → что дальше».
Точки остановки (⏸) — ждать ответа пользователя, больше нигде не останавливаться.

## 1. Analyst (сам, в главной сессии)
1. Прочитай `docs/PRD.md`, `docs/ai/README.md`, `docs/ai/architecture.md`; найди в коде, что уже есть по теме.
2. Уточни через `AskUserQuestion` только то, что меняет решение (до 4 вопросов за раз, у каждого — вариант
   по умолчанию «(Recommended)»): цель, сценарии, что вне scope, поведение в ошибках/пустых состояниях,
   где на экране. Не спрашивай то, что можно узнать из кода.
3. Номер задачи `NNNN` — `pnpm -s wt next`: последний в `docs/HISTORY.md` ветки `main` + 1 с учётом номеров
   в ещё не влитых ветках (параллельные задачи не возьмут один номер). Slug — kebab-case, англ.
4. Worktree задачи (скилл `worktree`): `pnpm wt new feature/NNNN-slug` — ветка от свежего `main`, ссылка на
   `.env.local`, зависимости. Дальше всё — в этом worktree; в основном checkout ничего не создавать и не править.
5. В worktree: `docs/specs/NNNN-slug.md` по `docs/specs/_template-feature.md` (критерии приёмки — проверяемые
   на экране утверждения); требование в нужный раздел `docs/PRD.md` (кратко + ссылка на spec, решения
   пользователя с датой); в конец таблицы «Задачи» в `docs/HISTORY.md` — строка задачи со статусом `в работе`
   (файл целиком не читай).
6. ⏸ Покажи пользователю краткое ТЗ (цель, AC, вне scope) и спроси «утверждаешь?». Правки → обнови spec.
   После «да» — статус spec `approved` и первый коммит ветки: spec, PRD, строка журнала (`NNNN: ТЗ — <название>`).

## 2. Developer
Вызови субагента `developer` (Agent, `subagent_type: developer`) с путём к spec, путём к worktree и номером задачи:
«Реализуй spec в этом worktree, верни отчёт по формату».
Если Developer вернул вопросы — задай их пользователю, ответы допиши в spec, вызови снова.

## 3. Локальный сервер и Tester
В worktree: `pnpm check && pnpm build` зелёные, затем `pnpm wt serve` — локальный сервер этого worktree (своя PGlite,
вход выключен, прод не трогается); адрес — из вывода.
Вызови субагента `tester` с путём к spec, путём к worktree и адресом сервера. Свой сервер он не запускает.
- FAIL → снова `developer` (через SendMessage тому же агенту, если доступен) с отчётом Tester → `pnpm check` →
  снова `tester` на том же сервере. Максимум 3 круга; потом ⏸ к пользователю с отчётом и вопросом, как быть.
- PASS → ⏸ покажи пользователю таблицу AC и скриншоты (`SendUserFile` или пути к png) и спроси:
  «На экране то, что заказывал?». «Не то: …» → допиши в spec, назад к Developer.
PR открывается только после PASS и «да» пользователя.

## 4. PR
Попроси `developer` открыть PR (draft не нужен). Описание — по шаблону `docs/ai/conventions.md`: что сделано,
сначала кратко, потом подробнее, ссылка на spec. Отчёт Tester и скриншоты пользователь уже видел на шаге 3 —
в описание PR их не копировать.

## 5. Reviewer и перепроверка
Вызови субагента `reviewer` с номером PR и spec.
- CHANGES REQUESTED → `developer` исправляет в worktree → `pnpm check` → `tester` снова проходит **все** AC на
  локальном сервере worktree (сервер упал или перезапускался — `pnpm wt serve`), чтобы правки ничего не сломали →
  снова `reviewer`. Максимум 3 круга, потом ⏸ к пользователю.
- APPROVED (label `ai-approved`) → дождись зелёного CI (`gh pr checks <N> --watch`).

## 6. Финал
Попроси `developer` последним коммитом в ветку задачи: spec — статус `done` и журнал (PR, круги тестов
и ревью); `docs/PRD.md` — требование ✅ и строка в «Журнале работ» (коммит — «см. git log»);
`docs/HISTORY.md` — у строки задачи PR и статус ✅. Так статусы
попадут в `main` вместе с мержем. Дождись зелёного CI. Сообщи пользователю: ссылка на PR, что сделано,
сколько было кругов, и ⏸ спроси, мержить ли.

## 7. После мержа (только по команде пользователя)
Мерж — по `.claude/skills/merge/SKILL.md` из основного checkout. Затем выкатка (`/flow release`) и уборка:
`pnpm wt remove feature/NNNN-slug` — остановит локальный сервер, удалит worktree и локальную ветку.

## 8. Закрытие сессии
Самое последнее сообщение сессии: по нему пользователь видит, можно ли её закрыть (решение пользователя 2026-10-15).
Так заканчивается любая сессия с изменениями, не только `/feature` и `/bug` (`CLAUDE.md` → «Конец сессии»). Итоговый
отчёт (в том числе отчёт `/flow` по этапам) — до блока, блок — последним. Перед ним:
1. Проверь сам, а не по памяти: PR влит (`gh pr view <N> --json state`), выкатка прошла (Vercel, смоук), то, что
   не проверялось локально, проверено на проде (для бага — исходные шаги воспроизведения на проде баг не повторяют);
   worktree задачи удалён (`pnpm wt list`), ветки нет ни на GitHub, ни локально
   (`git fetch --prune && git branch -a --list '*<ветка>'` — пусто); свои серверы и фоновые задачи остановлены;
   незакоммиченного и незапушенного нет; все ⏸ закрыты.
2. Оповести о том, что вскрылось и касается других: изменённые общие API и файлы, найденные баги, риск конфликтов
   с их PR. Кого оповещать — живые сессии проекта (`ListAgents`) и задачи в других worktree (`pnpm wt list`, их
   открытые PR). Сообщение — `SendMessage`; «в очереди у сессии» считается доставленным. Чужие задачи не бери — только
   сообщи. «Сообщать некому» пиши, только когда других сессий и worktree задач нет или новое их не касается.
3. Пункты 1–2 пройдены все — выведи блок, заполнив своими данными:
   ```text
   🎉✅ СЕССИЮ МОЖНО ЗАКРЫВАТЬ ✅🎉
   🔀 Смержено: PR #N → main (sha)
   🚀 Выкачено: Vercel ✅ · смоук ✅
   🔍 Проверено на проде: <что>
   🧹 Убрано: worktree, ветки, серверы, фоновые задачи
   📣 Агенты в курсе: <кому и что> (или «сообщать некому»)
   📌 Дальше (не долг этой сессии): <идеи и найденное на будущее> (или «ничего»)
   ```
   Не пройден хоть один пункт 1–2 — в том числе сообщение не доставлено или его некуда отправить, хотя новое касается
   другой задачи, — вместо него блок `⛔ СЕССИЮ ПОКА НЕ ЗАКРЫВАТЬ` со списком: что осталось (недоставленное —
   «<кому> — <что передать>»), кто и когда это сделает.

Если задачу отменили на любом шаге: закрой PR (если был), удали ветку на GitHub (`git push origin --delete <ветка>`)
и worktree (`pnpm wt remove <ветка> --force` — только по решению пользователя: изменения пропадут), spec — статус
`cancelled`, в `docs/HISTORY.md` — статус `отменена` (отдельным `chore`-PR, если ветки уже нет).

Тот же порядок шагов с остановками — в `.config/flows/feature.yaml` (`/flow feature "<требование>"`): там же видно,
на каком этапе задача (`/flow status`).

`gh` всегда только `GH_CONFIG_DIR="$HOME/.config/gh-personal" gh …`.
