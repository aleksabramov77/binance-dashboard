Описание бага от пользователя: $ARGUMENTS

Конвейер тот же, что в скилле `feature` (`.claude/skills/feature/SKILL.md`) — прочитай его и выполняй
шаги 2–7 без изменений: работа в worktree задачи (создан на шаге 1), проверка на локальном сервере до PR и
после правок по ревью, удаление worktree после мержа. Отличается только шаг 1 и требования к Developer. Тот же порядок
с остановками — `.config/flows/bug.yaml` (`/flow bug "<описание>"`).

## 1. Analyst (баг)
1. Собери факты сам, прежде чем спрашивать: строки из `data/logs/*.jsonl` (или страница `/logs`),
   связанный код, `git log` по затронутым файлам.
2. Уточни у пользователя (`AskUserQuestion`) только недостающее: шаги воспроизведения, ожидаемое поведение,
   серьёзность (по умолчанию `major`).
3. Номер задачи и worktree — как в шагах 1.3–1.4 скилла `feature`, ветка `bug/NNNN-slug` (срочный фикс прода —
   `hotfix/NNNN-slug`). В worktree: `docs/specs/NNNN-slug.md` по `docs/specs/_template-bug.md` и строка в
   `docs/HISTORY.md` (шаг 1.5 скилла `feature`). PRD меняй, только если баг означает изменение требования; иначе —
   строка в журнале этапов не нужна.
4. ⏸ Покажи пользователю краткое описание (шаги, ожидаемое, AC) и получи «да». После «да» — первый коммит ветки,
   как в шаге 1.6 скилла `feature`.

## Особенности для Developer
Передай явно: «Сначала тест, который воспроизводит баг и падает; потом фикс; заполни раздел „Причина“
в spec». Ветка `bug/NNNN-slug` (срочный фикс прода — `hotfix/NNNN-slug`),
коммиты `NNNN: …`.

## Tester
Помимо AC — пройти исходные шаги воспроизведения и подтвердить, что баг не повторяется.
